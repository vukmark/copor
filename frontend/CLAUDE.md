# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the Flutter side of the `copor` repository. See the root `CLAUDE.md` (one level up) for the overall system layout and the git rules (the user does all commits and merges). It is split into packages:

| Path | Package | Holds |
|------|---------|-------|
| `frontend/` | `copor_frontend` (the app) | `lib/main.dart`, `lib/modules.dart` (composition root), `lib/firebase_options.dart`, platform folders, assets, and **all Flutter tests** (`test/`) |
| `../packages/core/flutter/` | `copor_core` | everything else under `lib/src/` (described below) and `lib/copor_app.dart` |
| `../packages/<module>/flutter/` | `copor_<module>` | an optional module (`vu_meet`, `todo`, `cloud`, `calendar_entry`, `contacts`, `help`, `news`) |

Imports across packages use `package:copor_core/…` / `package:copor_<module>/…`; relative imports stay inside one package. Paths under `lib/src/` below are in `packages/core/flutter`.

**Before touching any module code, read [`FRONTEND_MODULE_CONVENTIONS.md`](../packages/core/flutter/lib/src/modules/FRONTEND_MODULE_CONVENTIONS.md) (in core's `lib/src/modules/`) first.** It is the authoritative, actively-maintained spec for folder structure, naming, DI lifecycle, bloc scoping, and data flow for every module — this file does not repeat it.

## Commands

Run these in `frontend/` unless noted:

```bash
flutter pub get              # install dependencies (all packages at once: `npm run flutter:get` at the root)
flutter run -d chrome         # run web build
flutter test                  # run all tests
flutter test test/path/to/some_test.dart   # run a single test file
flutter analyze                # static analysis (flutter_lints, see analysis_options.yaml) — run it in each package too
dart run build_runner build --delete-conflicting-outputs   # in packages/core/flutter or a module package: regenerate *.g.dart (Retrofit sources, json_serializable models)
dart run build_runner build --delete-conflicting-outputs   # in frontend/: regenerate the test mocks (test/mock_list.mocks.dart)
```

Run `build_runner` after adding/changing any Retrofit `@RestApi` interface or `@JsonSerializable` model — those `.g.dart` files are checked in but must be regenerated by hand, there's no watch mode wired into `flutter run`. The `lib` `.g.dart` files (core) and the test mocks (app) are in different packages, so neither build touches the other's output; within one package, a `--build-filter` run deletes generated outputs *outside* the filter — restore tracked ones with `git ls-files -d | xargs -r git checkout --`. If it fails with "Tried to delete from package not in the build", the cache references a deleted file — remove `.dart_tool/build` and rerun.

### Tests

Flutter only runs files named `*_test.dart`. Shared Mockito mocks are declared in `test/mock_list.dart`; the generated `test/mock_list.mocks.dart` is gitignored (`*.mocks.dart`), so run the test-mock build above on a fresh checkout or after adding a `MockSpec`. Widget tests that build `copor_scaffold` components need a `DSBreakpointsScope` above them (e.g. `MaterialApp(builder: (context, child) => DSBreakpointsScope(breakpoints: appBreakpoints, child: child!))`), as the real app root provides one.

The root `scripts/git-hooks/` (installed with `copor setup hooks`) runs `flutter pub get` automatically on checkout/merge when `pubspec.yaml`/`pubspec.lock` changed, so a fresh `pub get` after switching branches is usually not needed by hand.

## Architecture

### Sibling packages

`copor_theme` and `copor_scaffold` (in `../packages/`, local path deps in each `pubspec.yaml`) provide the design system and the `DSPageAppBar`/`DSPageDrawer`/`DSPageBottomNavBar` scaffold interfaces that every module's `<module>_scaffold.dart` implements. `copor_scaffold_dev` is a dev-only companion (widget preview harness, per the `dataviz`/showcase tooling — not shipped logic).

### `lib/src/` top level (core: `packages/core/flutter/lib/src/`)

- `modules/` — one folder per core feature (login, my account, search, administration, forms, table, …); optional modules are their own packages. See the conventions doc above.
- `data/`, `network/` — cross-module HTTP plumbing: `network/dio_factory.dart` builds the shared `Dio` client, `token_interceptor.dart`/`token_refresh_service.dart` handle JWT attach + silent refresh, `server_url_interceptor.dart` resolves the active backend URL, `public_routes.dart` lists endpoints that skip auth. Module-level `data_source/` folders build Retrofit clients on top of this shared `Dio` instance rather than creating their own.
- `error/` — `Failure`/`DataSource` model uniform error handling across the app: `DataSourceExtension.getFailure()` maps low-level failure kinds (timeout, no connection, 4xx/5xx, cache errors) to user-facing `Failure`s; `error_handler.dart` and `extract_error_message_helper.dart` turn a caught exception into one of these. Repository implementations return failures through this path rather than throwing raw `DioException`s up to blocs.
- `bloc/global_blocs/` — app-wide blocs (session, connectivity, etc.) that live outside any single module's scope.
- `core/` — cross-cutting device/platform concerns (`security/` biometric lock, `system/device_service.dart`), not business logic; plus `core/module/copor_module.dart`, the contract optional modules implement, and `core/module/app_modules.dart` (`AppModules`), where the app registers its modules and home route at startup — core reads `AppModules.enabled` and never imports the app.
- The app's `frontend/lib/modules.dart` (not in core) — the composition root: `enabledModules` (the optional modules this app includes) and `homeRoute`. See "Optional modules" in the conventions doc.
- `local_storage/`, `theme/`, `utils/`, `components/`, `config/` — self-explanatory; `components/` here is app-wide reusable widgets, distinct from a module's own `presentation/components/`.

### State management stack

`flutter_bloc`/`bloc` for state, `get_it` for DI, `go_router` for navigation, `dio` + `retrofit` for networking, `dartz` for functional error handling (`Either`), `flutter_hooks` for `HookWidget`s. All of this is used the way the module conventions doc describes — that document, not this one, is the source of truth for how to wire a new feature together.
